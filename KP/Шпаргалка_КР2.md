## 1. Задание 1 — проверка названия (`validateTaskDraft`, ПР4)

**Результат:** `"  Изучить localStorage  "` → `{ ok: true, value: { id: 20, title: 'Изучить localStorage', priority: 'high' } }`; `"   "` → `{ ok: false, errors: { title: 'Название не может состоять только из пробелов' } }`.

**Основные моменты:**

- Сначала `typeof draft.title !== "string"` — из `FormData` приходит строка, но функция может получить что угодно.
- `trim()` убирает пробелы по краям — это и есть **нормализация**. В `value` попадает уже обрезанное название.
- Длина проверяется **после** `trim`: `"   "` становится `""` → длина 0 → ошибка.
- HTML-атрибут `required` строку из пробелов пропускает (для него она непустая) — поэтому нужна своя проверка.
- Функция не бросает исключение, а возвращает `{ ok, errors }`, причём ошибки всех полей сразу.
- `id: "20"` (строка) превращается в число `20` — это видно в `value`.

**Вопросы:**

- *Почему не `if (!draft.title.trim())`?* Можно, но отдельная проверка длины даёт разные сообщения для «пусто» и «длиннее 100».
- *Почему `JSON.stringify(ok.value.title)` в выводе?* Чтобы были видны кавычки и отсутствие пробелов по краям.

## 2. Задание 2 — сохранение после перезагрузки (ПР4, `localStorage`)

**Результат:** после F5 задача 20 на месте (5 задач, 40.0%), статус «Данные восстановлены из localStorage.». В ключе `tip-js-practice-04:demo`:
`{"version":1,"tasks":[…,{"id":20,"title":"Изучить localStorage","completed":false,"priority":"high"}]}`.

**Как переснять скриншот с настоящим DevTools:**

1. `cd practice-04 ; npm.cmd start`, открыть `http://127.0.0.1:5504/` (именно `127.0.0.1`, не `localhost` — это разные origin, у каждого своё хранилище).
2. «Сбросить сохранённые данные» → фильтр «Все».
3. id `20`, «Изучить localStorage», «Высокий» → «Добавить задачу».
4. F5.
5. F12 → Application → Storage → Local Storage → `http://127.0.0.1:5504` → щёлкнуть строку `tip-js-practice-04:demo` (внизу раскроется JSON).
6. Скриншот, где видны список и панель. Заменить картинку 2 в документе.

**Цепочка:** `submit` → `validateTaskDraft` → `addTask` (новый массив) → `persistCurrentTasks` → `saveTasks` → `setItem(key, JSON.stringify({ version: 1, tasks }))`. При открытии: `loadTasks` → `getItem` → `JSON.parse` → проверки → `currentTasks`.

**Основные моменты:**

- `localStorage` хранит **только строки** → `JSON.stringify` при записи, `JSON.parse` при чтении.
- `getItem` несуществующего ключа даёт `null` — это «данных ещё нет», а не ошибка.
- `setItem`/`getItem` могут бросить исключение (квота, запрет хранилища), `JSON.parse` — `SyntaxError` → всё в `try/catch`.
- После `JSON.parse` проверяю `version === 1` и каждую задачу (`isValidTaskList`: типы, уникальные id). Корректный синтаксис ≠ корректные данные.
- При любой проблеме — исходный набор + предупреждение, приложение не падает.
- Объект хранилища передаётся аргументом (`loadTasks(window.localStorage, …)`) → в тестах подставляется имитация.

**Вопросы:**

- *Зачем `version`?* Если формат поменяется, старую запись можно распознать и не применять.
- *Почему не `localStorage.clear()` при сбросе?* Удалились бы ключи другого набора (`…:variant`). Удаляю только свой — `removeItem(storageKey)`.
- *`localStorage` vs `sessionStorage`?* Второй очищается при закрытии вкладки.

## 3. Задание 3 — задачи с сервера (`getTasks`, ПР5)

**Результат:** `id: [4, 13, 34]`, `meta.total: 3`, `meta.filters: { completed: false, priority: 'high', categoryId: null, q: '' }`.

**Что доказывает, что фильтрует сервер:** `meta.filters` прислал сервер — он сообщает, какие параметры получил. В клиенте нет `filter()` по массиву: `getTasks` только передаёт `query` дальше, а `buildUrl` превращает его в `…/api/tasks?completed=false&priority=high`.

**Основные моменты:**

- `createApiClient({ baseUrl, timeoutMs })` — общий HTTP-клиент; `createTaskApi(client)` — методы задач. Разделение: клиент не знает про задачи, `task-api` не знает про `fetch`.
- Фильтры проверяются **до** запроса (`normalizeFilters`): `completed` только boolean, `priority` только `low|medium|high`… Иначе `TypeError`, запрос не уходит.
- Query собирается через `URL` + `searchParams.set` — кодирует пробелы, `&`, кириллицу. **`false` не выкидывается** (пропускаю только `undefined`, `null`, `""`).
- Ответ проверяется **после**: `data` — массив, каждая задача по схеме, id уникальны, `meta.total === data.length`. Иначе `ApiError` с `kind: "invalid-response"`.
- `await` обязателен: без него в переменной Promise, а не `{ tasks, meta }`.

**Вопросы:**

- *Почему не взять все задачи и отфильтровать у себя?* Лишний трафик; в реальном API задач могут быть тысячи; условие задания — фильтрует сервер.
- *Что будет, если API не запущен?* `ApiError` с `kind: "network"` («Сервер недоступен»).

## 4. Задание 4 — HTTP-ошибка (`getTaskById(999)`, ПР5)

**Результат:** `kind: http`, `status: 404`, `code: TASK_NOT_FOUND`, `message: Задача с id 999 не найдена.`; затем «Программа продолжает работу».

**Пояснение (уже в документе):** `fetch` не отклоняет Promise на 4xx/5xx — сервер ответил. Без проверки `response.ok` тело ошибки `{"error": …}` было бы принято за данные.

**Основные моменты:**

- `response.ok === true` только для 200–299.
- `fetch` отклоняется лишь когда ответа нет (сеть, отмена) → это `network`/`timeout`/`aborted`.
- В `try` обёрнут **только** вызов `fetchFn`. Проверка `response.ok` стоит после — поэтому брошенный там `ApiError("http")` не попадает в сетевой `catch` и не превращается в `network`.
- Поля ошибки берутся из тела `{ error: { code, message, details } }`; если тело не JSON — всё равно `kind: "http"` и числовой `status`.
- Опираться нужно на `status`/`code`, а не на текст сообщения: текст может измениться.

**Вопросы:**

- *Что сделает код при 503?* То же: `kind: "http"`, `status: 503`, `code: SERVICE_UNAVAILABLE` (можно показать: `client.requestJson("/debug/error")`).
- *А при битом JSON с кодом 200?* `kind: "invalid-response"` (`/debug/invalid-json`).

## 5. Задание 5 — изменение через API (ПР6, `PATCH`)

**Результат:** до — `[4, 7, 13, 19, 22, 28, 34]`, после нажатия «Выполнена» у 4 — `[7, 13, 19, 22, 28, 34]`. Запросы: `PATCH /api/tasks/4` → **200** (тело `{"completed":true}`), `OPTIONS /api/tasks/4` → 204 (CORS preflight), `GET /api/tasks?completed=false` → **200**.

**Как переснять скриншот с настоящим Network:**

1. Остановить ПР5, `cd practice-06 ; npm.cmd start`, открыть `http://127.0.0.1:5506/`.
2. «Восстановить учебные данные» → OK.
3. В фильтрах «Статус: В работе» (остальное «Все») → «Применить».
4. F12 → Network → фильтр **Fetch/XHR** → очистить журнал (🚫).
5. «Выполнена» у задачи «Подготовить модель задач» (id 4).
6. Скриншот, где видны список и строки `4` (PATCH, 200) и `tasks?completed=false` (GET, 200). Колонку Method можно включить правым кликом по заголовку таблицы.

**Цепочка:** клик → `dom-app.js` (делегирование, `data-action="toggle"`) → `controller.toggleTask(4)` → берёт текущий `completed` из последнего ответа → `mutate(...)`: блокирует кнопки → `api.setTaskCompleted(4, true)` → `updateTask` → `requestJson("/tasks/4", { method: "PATCH", body: { completed: true } })` → сообщение «Задача выполнена.» → `load()` → `GET /tasks?completed=false` → перерисовка → разблокировка в `finally`.

**Основные моменты:**

- **Сервер — источник истины.** Список не правлю руками: после PATCH заново запрашиваю его с текущими фильтрами. Задача 4 теперь `completed: true` → сервер её в выборку `completed=false` не включает.
- `PATCH` — частичное изменение: отправляю только `{ completed: true }`.
- `Content-Type: application/json` + `JSON.stringify` добавляются только когда есть тело.
- `OPTIONS` в Network — preflight: приложение (5506) и API (5505) — разные origin, а PATCH с JSON-телом требует разрешения сервера (`Access-Control-Allow-Methods`).
- `setMutationPending(true/false)` в `try/finally` — двойной клик не отправит второй PATCH, а при ошибке кнопки всё равно разблокируются.
- Повторная загрузка защищена от гонок: `AbortController` + номер запроса.

**Вопросы:**

- *Почему не удалить карточку сразу, без GET?* Это оптимистичное обновление: если сервер откажет, интерфейс покажет неправду. В ПР6 — только подтверждённое сервером состояние.
- *Чем PATCH отличается от POST?* POST создаёт новую задачу (id назначает сервер, ответ 201), PATCH меняет поля существующей (200).
- *Что вернёт DELETE?* `204` без тела — клиент возвращает `null`, `json()` не вызывает.

## 7. Коротко — главные идеи

- **Три уровня проверки:** HTML-атрибуты → своя валидация (`trim`, правила модели) → проверка данных после `JSON.parse` / после ответа сервера.
- **`localStorage` — строки:** `JSON.stringify` / `JSON.parse` в `try/catch`, затем проверка формата и `version`.
- **`fetch` не падает на 404:** статус проверяется явно через `response.ok`.
- **Пять видов ошибок:** `http`, `network`, `invalid-response`, `timeout`, `aborted`.
- **Фильтры — на сервер** через query-параметры (`URLSearchParams`), не через `filter()` у себя.
- **После изменения — повторный GET**: интерфейс показывает только то, что подтвердил сервер.
