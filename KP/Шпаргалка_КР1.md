## 1. Задание 1 — сводка выполнения (`practice-01/js/progress.js`)

**Что делает:** по `totalTasks` и `completedTasks` печатает всего / выполнено / осталось / процент / статус, либо «Задач пока нет», либо одну строку «Ошибка: …».

**Результаты:** (12, 5) → осталось 7, 41.7%, «В работе»; (0, 0) → «Задач пока нет»; (5, 6) → «Ошибка: выполнено больше, чем существует.»

**Порядок проверок (это главное):**

1. `typeof … !== "number"` — строка `"5"` сразу ошибка. Строки **не преобразуем**: по условию так нельзя, а `Number("")` дал бы 0.
2. `Number.isNaN` — `NaN` имеет тип `number`, поэтому его ловим отдельно.
3. `Number.isInteger` — отсекаем 2.5.
4. `< 0` — отрицательные.
5. `totalTasks > 1000` — верхняя граница.
6. `completedTasks > totalTasks` — выполнено больше, чем есть.
7. Только потом нулевой случай `0, 0` (иначе было бы деление на ноль → `NaN`).
8. Потом обычный расчёт.

**Процент:** `((completed / total) * 100).toFixed(1)`. `toFixed` возвращает **строку**, поэтому он только для вывода.

**Статус** определяется по исходным числам, а не по округлённому проценту:
`completed === 0` → «Не начато», `completed === total` → «Завершено», иначе «В работе».
Округлённый процент — уже строка и уже неточное значение. Если бы, например, разрешили 2000 задач, 1999 из 2000 дало бы «100.0%», хотя одна задача не сделана. Поэтому статус зависит от точных чисел, а округление — только для вывода.

**Почему есть `task1-runs.mjs`:** в `progress.js` значения заданы константами (сейчас там мой вариант 20/11). Скрипт читает файл, подставляет три пары значений и выполняет его через `node:vm`. Сам `progress.js` не меняется — это сказано в подписи к скриншоту.

**Возможные вопросы:**

- *Почему `===`, а не `==`?* `==` приводит типы: `5 == "5"` даёт true. `===` сравнивает и тип, и значение.
- *Почему проверка `NaN` отдельная?* `typeof NaN === "number"`, а `NaN < 0` и `NaN > 1000` оба `false` — без отдельной проверки он прошёл бы дальше.
- *Где `const`, где `let`?* Здесь всё `const` (кроме `status`, который присваивается в ветках): значения не переприсваиваются.

## 2. Задание 2 — отбор невыполненных (`getPendingTasks`)

```js
function getPendingTasks(tasks) {
  return tasks.filter((task) => task.completed === false);
}
```

**Результаты:** для `demoTasks` → id `[4, 7]`; для `[]` → `[]`; исходный массив не изменился.

**Основные моменты:**

- `filter` всегда возвращает **новый массив**, исходный не трогает. Порядок сохраняется.
- Для пустого массива — пустой массив, а не `undefined` и не ошибка.
- Сравнение именно `=== false`, а не `!task.completed`: так видно намерение, и, например, `undefined` не посчитается невыполненной задачей.
- Объекты внутри нового массива — **те же самые** (не копии). Это нормально: мы их не меняем.

**Возможные вопросы:**

- *Чем `filter` отличается от `find` и `map`?* `find` — первый подходящий элемент или `undefined`; `filter` — все подходящие (новый массив); `map` — новый массив преобразованных значений.
- *Что будет, если внутри callback написать `task.completed = true`?* Изменится исходный объект — `filter` от этого не защищает. Поэтому в callback только читаем.

## 3. Задание 3 — изменение статуса (`setTaskCompleted`)

Цепочка функций:

```
setTaskCompleted(tasks, id, completed)
  ├─ completed не boolean? → { ok: false, error }
  └─ updateTask(tasks, id, { completed })
        ├─ checkId(id): число? положительное безопасное целое?
        ├─ findTaskById(tasks, id) === undefined? → { ok: false, error: "Задача с id … не найдена" }
        └─ { ok: true, tasks: tasks.map(task => task.id === id ? { ...task, ...changes } : task) }
```

**Результаты:** для id 4 → новая запись `completed: true`, в исходном `demoTasks` — `false`, объект новый (`!==`). Для id 777 → `{ ok: false, error: 'Задача с id 777 не найдена' }`, данные не изменились.

**Основные моменты:**

- **Не меняем входные данные.** `map` создаёт новый массив; для нужной задачи `{ ...task, ...changes }` создаёт **новый объект**, остальные объекты переиспользуются как есть (их никто не меняет).
- **Порядок spread важен:** `{ ...task, completed }` — новое значение перекрывает старое. Если написать `{ completed, ...task }`, старое значение перезапишет новое.
- **Ошибки — это данные, а не исключения.** Возвращаем `{ ok: false, error }`, программа не падает, вызывающий код сам решает, что показать.
- **`checkId`:** `typeof id !== "number"` (строку `"4"` не принимаем), `Number.isSafeInteger(id) && id > 0` (отсекает 0, -1, 1.5, NaN, Infinity, слишком большие числа).
- **Статус — строго `true`/`false`.** Строка `"false"` не подходит: `Boolean("false")` — это `true`.
- `findTaskById` ищет через `find` по `id`, **а не по индексу**: у задачи id 4 индекс 1.

**Возможные вопросы:**

- *Почему нельзя просто `task.completed = true`?* Это изменит исходный объект: старое состояние потеряется, а в интерфейсе ПР3 сломается логика «старый массив → новый массив».
- *Что значит «поверхностная копия»?* `[...arr]` или `map` копируют только массив; объекты внутри остаются теми же. Поэтому изменённой задаче нужен свой новый объект.
- *Почему `id` не индекс?* После удаления индексы сдвигаются, а `id` постоянный. В `demoTasks` есть id 10, но индекса 10 нет.

## 4. Задание 4 — переключение в браузере (`practice-03/src/main.js`)

**Как из нажатия получается изменение задачи (это и есть пояснение в документе):**

1. Обработчик назначен **один раз** на весь список: `elements.list.addEventListener("click", handleTaskListClick)`.
2. Нажали на подпись внутри кнопки → событие **всплывает** до `ul`. `event.target` — это `span`, поэтому кнопку ищем через `event.target.closest("button[data-action]")` и проверяем `elements.list.contains(button)`.
3. Действие — из `button.dataset.action` (`toggle` / `delete`), неизвестное игнорируем.
4. Карточка — `button.closest("li[data-task-id]")`. В `dataset` всё **строки**: `"4"` → `Number(...)` → `4`, затем проверка `Number.isSafeInteger(id) && id > 0` (так `"4abc"` → `NaN` → ошибка, а не 4).
5. Текущий статус берём **из массива** через `findTaskById`, не из текста кнопки или CSS-класса.
6. `setTaskCompleted(currentTasks, id, !task.completed)` → при `ok` сохраняем `currentTasks = result.tasks`.
7. `renderApp()` заново считает видимые задачи по фильтру, перерисовывает карточки, сводку и пустое состояние. Задача 4 теперь выполнена → в фильтре «В работе» её нет → остаётся только id 7.
8. `restoreTaskFocus(id, action)` возвращает фокус на кнопку (если карточка исчезла — на активный фильтр).

**Почему сводка 75.0%, а «Показано» 1:** сводка считается по **всему** `currentTasks` (4 задачи, 3 выполнены), а «Показано» — по отфильтрованной выборке. Фильтр меняет только то, что видно, а не данные.

**Возможные вопросы:**

- *Зачем делегирование?* Карточки пересоздаются при каждой отрисовке. Обработчик на `ul` переживает перерисовку, и не нужно вешать обработчики на каждую кнопку.
- *Почему не `event.target.dataset.action`?* При клике по `span` `target` — это `span`, у него нет `data-action`.
- *Чем `target` отличается от `currentTarget`?* `target` — где реально кликнули (`span`), `currentTarget` — чей обработчик сейчас работает (`ul`).
- *Если просто удалить `li` через `element.remove()`?* После следующей отрисовки задача вернётся: данные-то не изменились.
- *Почему названия через `textContent`, а не `innerHTML`?* Название выводится как текст: `<strong>` в названии не станет тегом.
- *Почему после перезагрузки всё сбрасывается?* В ПР3 сохранения нет, данные только в памяти. Сохранение в `localStorage` сделано в ПР4.

## 6. Коротко — главные идеи

- **Строгие проверки без приведения типов**: `===`, `typeof`, `Number.isInteger` / `Number.isSafeInteger`; строку никогда не превращаем в число молча.
- **Порядок: ошибки → особый случай → обычный расчёт.**
- **Функции возвращают значение, а не печатают**; вывод — отдельно.
- **Входные данные не изменяются**: `filter` / `map` / spread дают новые массивы и объекты.
- **Ошибки — объект `{ ok: false, error }`**, а не падение программы.
- **В браузере: событие → id из `dataset` → функция сервиса → новый массив → `renderApp()`**. Данные — источник правды, DOM строится из них.
